## Why ray casting is the bottleneck

The particle filter scores each guess of the car's pose by casting rays into the map and comparing them with the real LiDAR scan. With 4,000 particles and 61 rays each, that's 244,000 rays every update. Every ray is independent, so the work is embarrassingly parallel and a natural fit for the GPU.

## What the port took

range_libc ships a CUDA path, but not one that runs on a Jetson Orin Nano under Python 3.

- Ported the Python 2 wrapper to Python 3.
- Retargeted the CUDA build from `sm_20` to `sm_87`, the Orin's architecture.
- Replaced `tf.transformations` with inline quaternion math.
- Added a shim for the missing `distutils.msvccompiler` module.

## Result

| Backend | Time per update | Rate |
|---|---|---|
| CPU (`PyRayMarching`) | 5.37 ms | 186 Hz |
| GPU (`PyRayMarchingGPU`) | 1.20 ms | 833 Hz |

Both runs use 4,000 particles and 61 rays per particle. The benchmark is `scripts/bench_rangelibc.py` in the [F1TENTH repo](https://github.com/ryanxxhuang/f1tenth).
